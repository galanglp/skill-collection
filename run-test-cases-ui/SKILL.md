# UI Test Case Execution

## Purpose
Execute a set of predefined test cases (typically generated by the `test-case-generator` skill) against a web application UI using Chrome DevTools via MCP. The goal is to automate the execution of manual test cases, verify expected results, and report any discrepancies.

## Pre-requisites
1. A markdown file containing test cases in a table format (e.g., `docs/test-cases/<feature-name>.md`).
2. The web application must be running and accessible.
3. The `chrome-devtools` skill must be available for interacting with the browser.

## Instructions for the Agent

When invoked, follow these steps systematically:

### 1. Preparation
- Ask the user for the path to the test case markdown document if not provided.
- Ask the user for the base URL of the web application to test.
- Read the test cases document to understand the "System Flow Summary" and the scenarios.
- Make sure you are familiar with the `chrome-devtools` skill to understand how to use the MCP tools for browser automation.

### 2. Execution Loop
For each test case in the document (or a specific subset if requested by the user):

1. **Setup**: Use `new_page` or `navigate_page` to go to the starting URL for the test case.
2. **Execute Steps**:
   - For each step in the test case:
     - Use `take_snapshot` to get the current page structure and find the `uid` of the elements you need to interact with.
     - Use appropriate tools (`click`, `fill`, `evaluate_script`, etc.) to perform the action.
     - Wait for necessary network requests or DOM changes before proceeding. Take a new snapshot to confirm state changes if needed.
3. **Verification**:
   - Compare the current state of the UI against the "Expected Result" of the test case.
   - Use `take_snapshot` to verify text or element presence.
   - You may use `take_screenshot` if visual verification is necessary or to document a failure.
4. **Recording**:
   - Mark the test case as PASS if the actual result matches the expected result.
   - Mark the test case as FAIL if it does not. On failure, capture the reason and optionally save a screenshot.

### 3. Reporting
After executing the test cases, create a Test Execution Report artifact (e.g., `docs/test-runs/run-<date>-<feature>.md`). Write it directly to the user's project repository.

- **Execution Date**:
- **Base URL**:
- **Summary**: X Total, Y Passed, Z Failed
- **Detailed Results**:
  | ID | Scenario | Status | Notes | Screenshot (if failed) |
  |----|----------|--------|-------|------------------------|

## Important Rules for Browser Automation
- **Always take a fresh snapshot** after a navigation or interaction that changes the DOM before trying to interact with new elements. `uid`s can change.
- **Handle timing issues gracefully**: If an element is not found, it might still be loading. Consider waiting and retrying the snapshot.
- **Clean state**: Try to ensure each test case starts from a clean state (e.g., clear cookies/localStorage if needed, or explicitly navigate to a fresh starting point).
- **Graceful Failure**: If a test case fails early, document the failure and move on to the next independent test case, rather than stopping the entire execution.
